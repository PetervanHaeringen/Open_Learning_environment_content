# 최종 과제 — 완전한 Git 워크플로우

이론, 시각화, 그리고 실습 단계를 모두 거쳐왔습니다.
이제 이 모든 것을 하나로 모을 차례입니다: 연습용 저장소에서 완전한 전문가 수준의 워크플로우를 진행합니다.

---

## 무엇을 하게 될까요

실제 팀에서 테스터가 매일 수행하는 단계를 그대로 밟아봅니다:

```
이슈 만들기
      ↓
브랜치 만들기
      ↓
테스트 파일 작성 + 커밋
      ↓
GitHub로 푸시
      ↓
풀 리퀘스트 열기
      ↓
리뷰 받고 처리하기
      ↓
병합 (선생님 또는 동료가 수행)
      ↓
이슈 닫기
```

---

## 과제 내용

### 1단계 — 이슈 만들기

`git-garden-playground` 저장소에 이슈를 만듭니다.

시나리오: 당신이 배운 주제에 대한 설명이 `handleidingen/` 폴더에 빠져 있다는 것을 발견했다고 가정합니다.

다음 내용을 포함한 이슈를 작성하세요:
- 명확한 제목
- 무엇이 빠졌는지에 대한 설명
- 라벨: `documentation`
- 마일스톤: `Git Garden v1.0` (존재한다면; 존재하지 않으면 비워두세요)

이슈 번호를 적어두세요 — 나중에 필요합니다.

---

### 2단계 — 브랜치 만들기

```bash
git switch main
git pull
git switch -c docs/handleiding-[당신의-이름]
```

`docs/`로 시작하는, 설명적인 브랜치 이름을 사용하세요.

---

### 3단계 — 파일 작성하기

`handleidingen/` 폴더 안에 파일을 만드세요:

**`handleidingen/[당신의-이름]-samenvatting.md`**

이 Git 학습 과정에서 배운 내용에 대한 짧은 요약을 그 안에 작성하세요.
최소한 다음 내용을 포함하세요:
- 이전에는 이해하지 못했지만 지금은 이해하게 된 것 3가지
- 가장 유용하다고 생각하는 명령어 1개
- 실제 업무에서 Git을 사용하고 싶은 상황 1가지

---

### 4단계 — 커밋하기

```bash
git add handleidingen/[당신의-이름]-samenvatting.md
git commit -m "[당신의 이름]의 Git 요약 추가 (Closes #[이슈-번호])"
```

---

### 5단계 — 푸시하기

```bash
git push origin docs/handleiding-[당신의-이름]
```

---

### 6단계 — 풀 리퀘스트 열기

GitHub로 이동해서 풀 리퀘스트를 엽니다.

**PR 설명에 필요한 내용:**
- 무엇을 추가했나요?
- 이것이 다른 사람들에게 왜 유용한가요?
- 이슈 참조: `Closes #[번호]`
- 리뷰어가 특히 확인해야 할 점 1가지

---

### 7단계 — 리뷰 처리하기

선생님이나 동료 학생이 당신의 PR을 리뷰할 것입니다.
피드백이 있다면:
1. 로컬 브랜치에서 파일을 수정하세요
2. 명확한 메시지와 함께 그 변경 사항을 커밋하세요
3. 변경 사항을 푸시하세요 — PR이 자동으로 업데이트됩니다

---

### 8단계 — 병합하기

승인된 후에는, 선생님이나 (권한이 허용된다면) 당신 자신이 PR을 병합합니다.

그런 다음 확인하세요:
```bash
git switch main
git pull
ls handleidingen/
```

이제 당신의 파일은 `main`에 들어가 있습니다. 공식 저장소의 일부가 된 것입니다.

---

## 평가 기준

| 항목 | 좋은 기준 |
|-----------|------|
| 이슈 | 명확한 제목, 설명, 올바른 라벨 |
| 브랜치 이름 | 설명적이며, `docs/`로 시작함 |
| 커밋 메시지 | 설명적이며, 이슈 번호를 참조함 |
| 파일 | 요구 사항을 충족하며, 직접 작성한 내용 |
| PR 설명 | 완전하며, Closes #번호를 포함함 |
| 피드백 처리 | 명확한 메시지가 담긴 새 커밋 |

---

## 다 끝났나요?

모든 것이 병합되었다면, 당신은 다음을 증명한 것입니다:
- 완전한 Git 워크플로우를 스스로 수행할 수 있다는 것
- 이슈와 풀 리퀘스트에서 전문적으로 소통할 수 있다는 것
- 워크플로우를 흐트러뜨리지 않으면서 피드백을 처리하는 방법을 안다는 것

이것은 네 가지 명령어로 하는 잔재주가 아닙니다 — 이것이 바로 전문가처럼 일하는 방식입니다.
