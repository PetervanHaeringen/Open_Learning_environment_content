# モジュール7 — コンフリクトと品質

共同作業は、いつもスムーズにいくとは限りません。
何かをマージしようとしたとき、Gitがこう言うことがあります。「これは自分だけでは判断できない。」
それはエラーではありません——あなたに向けられた問いかけなのです。

---

## 1. マージコンフリクトとは何か？

マージコンフリクトは、2つのブランチが**同じ行を、それぞれ違う形で変更した**ときに発生します。

Gitは、どちらのバージョンが正しいのかを自分では判断できません。
コンフリクトしている行に印をつけて、あなたの判断を待ちます。

例：`main`では、`README.md`の1行目がこうなっているとします：
```
Versie: 1.0
```

あなたのブランチでは、こう変更しました：
```
Versie: 2.0
```

そして、別のブランチではこうなっています：
```
Versie: 1.5
```

どちらが正しいのでしょうか？Gitにはわかりません。でも、あなたにはわかります。

---

## 2. コンフリクトはどんな見た目か？

Gitはファイルを開き、次のようなマーカーを挿入します：

```
<<<<<<< HEAD
Versie: 2.0
=======
Versie: 1.5
>>>>>>> 別のブランチ
```

- `<<<<<<< HEAD` と `=======` の間にあるのは、あなたのバージョンです
- `=======` と `>>>>>>>` の間にあるのは、もう一方のブランチのバージョンです
- どちらを残すかは、あなたが決めます

---

## 3. コンフリクトを解決する：手順を追って

```bash
# マージを試みる
git merge 別のブランチ

# Gitがこう報告します：CONFLICT (content) in README.md
# エディタでそのファイルを開く
```

**エディタの中で：**
1. コンフリクトのマーカー（`<<<<<<<`、`=======`、`>>>>>>>`）を探す
2. どちらのバージョンが正しいかを決める——または両方を組み合わせる
3. すべてのマーカーを削除する
4. ファイルを保存する

**ターミナルに戻って：**
```bash
git add README.md
git commit -m "コンフリクトを解決：バージョン番号を2.0に設定"
```

これでコンフリクトは解決しました。マージコミットが作成されました。

---

## 4. コンフリクトを防ぐには

コンフリクトを避けるための最良の方法：**小さく、頻繁なコミットとマージ**です。

マージを先延ばしにすればするほど、誰かが同じ行を変更している可能性が高まります。

良い習慣：
- ブランチの寿命を短く保つ——週単位ではなく、日単位で作業する
- 定期的にpullする：自分のブランチで `git pull origin main` を実行し、最新の状態を保つ
- 誰がどの部分を担当しているかを話し合っておく

---

## 5. コードレビュー：マージ前の品質チェック

**コードレビュー**とは、誰かの作業がマージされる前に、それを確認することです。

レビュアーとして注目すべき点：
- その変更は理解しやすいか？
- 予期しない影響はないか？
- コミットメッセージは明確か？
- 誤字や不整合はないか？

テスターであるあなたは、レビューがとても得意です——境界値やリスクを考える発想は、すでに身についているからです。

**良いレビューの作法：**
- 要求ではなく、質問の形で伝える：「これは間違っている」ではなく「〜については考えましたか？」
- 良い点についても触れる
- 自分のエゴはレビューの外に置く——大切なのはプロダクトそのものです

## 6. タグとリリース

**タグ**とは、特定のコミットに付ける名前のことです。
バージョン番号に便利です：`v1.0`、`v2.3.1`など。

```bash
# 軽量タグを作成する
git tag v1.0

# 注釈付きタグを作成する（説明付き）
git tag -a v1.0 -m "最初の安定版"

# タグをGitHubにプッシュする
git push origin v1.0
```

GitHub上では、タグから**リリース**を作成できます。
リリースには次のものが含まれます：
- その時点でのコード
- リリースノート（新機能、修正内容）
- 必要に応じて添付ファイル（インストールファイルなど）

テスターにとって、リリースはテストラウンドの出発点となります。
