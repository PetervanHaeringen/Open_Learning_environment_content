# Модуль 7 — Конфликты и качество

Совместная работа не всегда идёт гладко.
Иногда вы пытаетесь что-то слить, а Git говорит: «сам я с этим не справлюсь».
Это не ошибка — это вопрос, обращённый к вам.

---

## 1. Что такое конфликт слияния (merge conflict)?

Конфликт слияния возникает, когда две ветки **изменили одну и ту же строку по-разному**.

Git сам не может решить, какая версия правильная.
Он помечает конфликтующие строки и ждёт вашего решения.

Пример: в `main` первая строка `README.md`:
```
Versie: 1.0
```

В вашей ветке вы изменили её на:
```
Versie: 2.0
```

А в другой ветке написано:
```
Versie: 1.5
```

Кто прав? Git не знает. А вы знаете.

---

## 2. Как выглядит конфликт?

Git открывает файл и вставляет метки:

```
<<<<<<< HEAD
Versie: 2.0
=======
Versie: 1.5
>>>>>>> другая-ветка
```

- Всё между `<<<<<<< HEAD` и `=======` — это ваша версия
- Всё между `=======` и `>>>>>>>` — это версия другой ветки
- Вы решаете, что остаётся

---

## 3. Разрешение конфликта: шаг за шагом

```bash
# Вы пытаетесь выполнить слияние
git merge другая-ветка

# Git сообщает: CONFLICT (content) in README.md
# Откройте файл в своём редакторе
```

**В редакторе:**
1. Найдите метки конфликта (`<<<<<<<`, `=======`, `>>>>>>>`)
2. Решите, какая версия верна — или объедините их
3. Удалите все метки
4. Сохраните файл

**Снова в терминале:**
```bash
git add README.md
git commit -m "Конфликт разрешён: номер версии установлен на 2.0"
```

Конфликт разрешён. Коммит слияния создан.

---

## 4. Как предотвратить конфликты

Лучший способ избежать конфликтов: **маленькие, частые коммиты и слияния**.

Чем дольше вы ждёте со слиянием, тем выше вероятность, что кто-то другой изменил те же строки.

Хорошие привычки:
- Держите ветки недолговечными — работайте днями, а не неделями
- Регулярно делайте pull: `git pull origin main` в своей ветке, чтобы оставаться в курсе
- Обсуждайте, кто над какой частью работает

---

## 5. Код-ревью: качество перед слиянием

**Код-ревью (code review)** — это просмотр чужой работы перед тем, как её сольют.

В роли ревьюера обращайте внимание на:
- Понятно ли изменение?
- Есть ли неожиданные последствия?
- Понятны ли сообщения коммитов?
- Есть ли опечатки или несоответствия?

Как тестировщик, вы отлично справляетесь с ревью — вы уже привыкли мыслить в терминах граничных случаев и рисков.

**Хороший этикет ревью:**
- Задавайте вопросы, а не выдвигайте требования: «А вы подумали о...?» вместо «Это неправильно».
- Отмечайте и то, что сделано хорошо
- Оставьте своё эго за рамками ревью — речь идёт о продукте

## 6. Теги и релизы

**Тег (tag)** — это имя, которое вы даёте определённому коммиту.
Полезно для номеров версий: `v1.0`, `v2.3.1`.

```bash
# Создать облегчённый тег
git tag v1.0

# Создать аннотированный тег (с описанием)
git tag -a v1.0 -m "Первая стабильная версия"

# Отправить тег на GitHub
git push origin v1.0
```

На GitHub вы можете создать **релиз** из тега.
Релиз содержит:
- код на тот момент времени
- заметки о релизе (что нового, что исправлено)
- при необходимости вложения (установочные файлы)

Для тестировщика релиз — это отправная точка тестового цикла.
