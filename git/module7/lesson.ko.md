# 모듈 7 — 충돌과 품질

협업이 항상 순조롭게 흘러가지는 않습니다.
때로는 무언가를 병합하려고 할 때 Git이 이렇게 말합니다: "이건 저 혼자서는 판단할 수 없습니다."
이것은 오류가 아닙니다 — 당신에게 던지는 질문입니다.

---

## 1. 병합 충돌(merge conflict)이란 무엇인가?

병합 충돌은 두 브랜치가 **같은 줄을 서로 다른 방식으로 변경했을 때** 발생합니다.

Git은 어떤 버전이 옳은지 스스로 결정할 수 없습니다.
충돌하는 줄을 표시하고, 당신의 판단을 기다립니다.

예시: `main`에서, `README.md`의 첫 번째 줄이 다음과 같다고 합시다:
```
Versie: 1.0
```

당신의 브랜치에서는 이렇게 바꿨습니다:
```
Versie: 2.0
```

그리고 다른 브랜치에는 이렇게 되어 있습니다:
```
Versie: 1.5
```

누가 맞을까요? Git은 모릅니다. 하지만 당신은 압니다.

---

## 2. 충돌은 어떤 모습으로 나타날까?

Git은 파일을 열고 다음과 같은 표시를 삽입합니다:

```
<<<<<<< HEAD
Versie: 2.0
=======
Versie: 1.5
>>>>>>> 다른-브랜치
```

- `<<<<<<< HEAD`와 `=======` 사이에 있는 것은 당신의 버전입니다
- `=======`와 `>>>>>>>` 사이에 있는 것은 다른 브랜치의 버전입니다
- 무엇을 남길지는 당신이 결정합니다

---

## 3. 충돌 해결하기: 단계별로

```bash
# 병합을 시도합니다
git merge 다른-브랜치

# Git이 다음과 같이 알립니다: CONFLICT (content) in README.md
# 에디터에서 그 파일을 엽니다
```

**에디터에서:**
1. 충돌 표시(`<<<<<<<`, `=======`, `>>>>>>>`)를 찾습니다
2. 어떤 버전이 맞는지 결정합니다 — 또는 두 버전을 합칩니다
3. 모든 표시를 삭제합니다
4. 파일을 저장합니다

**다시 터미널로 돌아가서:**
```bash
git add README.md
git commit -m "충돌 해결: 버전 번호를 2.0으로 설정"
```

이제 충돌이 해결되었습니다. 병합 커밋이 생성되었습니다.

---

## 4. 충돌 예방하기

충돌을 피하는 가장 좋은 방법: **작고 빈번한 커밋과 병합**입니다.

병합을 미루면 미룰수록, 다른 누군가가 같은 줄을 바꿨을 가능성이 커집니다.

좋은 습관들:
- 브랜치의 수명을 짧게 유지하세요 — 몇 주가 아니라 며칠 단위로 작업하세요
- 정기적으로 pull하세요: 자신의 브랜치에서 `git pull origin main`을 실행해 최신 상태를 유지하세요
- 누가 어떤 부분을 작업하는지 미리 이야기하세요

---

## 5. 코드 리뷰: 병합 전의 품질 확인

**코드 리뷰(code review)**란, 다른 사람의 작업이 병합되기 전에 그것을 살펴보는 것을 말합니다.

리뷰어로서 다음을 주의 깊게 살펴보세요:
- 그 변경 사항이 이해하기 쉬운가요?
- 예상치 못한 영향이 있나요?
- 커밋 메시지가 명확한가요?
- 오타나 일관성 없는 부분은 없나요?

테스터인 당신은 리뷰에 아주 능숙합니다 — 이미 경계 사례와 위험 요소를 중심으로 생각하는 습관이 있기 때문입니다.

**좋은 리뷰 매너:**
- 요구하기보다 질문하세요: "이 부분은 고려해 보셨나요?"처럼, "이건 틀렸어요"보다 낫습니다
- 좋은 점도 함께 언급하세요
- 자존심은 리뷰 밖에 두세요 — 중요한 것은 결과물 그 자체입니다

## 6. 태그와 릴리스

**태그(tag)**는 특정 커밋에 붙이는 이름입니다.
버전 번호를 표시하는 데 유용합니다: `v1.0`, `v2.3.1`.

```bash
# 가벼운(lightweight) 태그 만들기
git tag v1.0

# 설명이 포함된(annotated) 태그 만들기
git tag -a v1.0 -m "첫 번째 안정 버전"

# 태그를 GitHub로 푸시하기
git push origin v1.0
```

GitHub에서는 태그로부터 **릴리스(release)**를 만들 수 있습니다.
릴리스에는 다음이 포함됩니다:
- 그 시점의 코드
- 릴리스 노트 (새로운 점, 수정된 점)
- 필요하다면 첨부 파일 (설치 파일 등)

테스터에게 릴리스란, 테스트 라운드의 출발점입니다.
