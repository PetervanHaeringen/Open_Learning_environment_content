# الوحدة 7 — التعارضات والجودة

التعاون لا يسير دائمًا بسلاسة.
أحيانًا تحاول دمج شيء ما، فيقول لك Git: "لا أستطيع فعل هذا بمفردي."
هذا ليس خطأً — إنه سؤال موجّه إليك.

---

## 1. ما هو تعارض الدمج (merge conflict)؟

يحدث تعارض الدمج عندما يقوم فرعان **بتغيير نفس السطر بطريقتين مختلفتين**.

لا يستطيع Git أن يقرر بنفسه أي نسخة هي الصحيحة.
فيقوم بتمييز الأسطر المتعارضة وينتظر قرارك.

مثال: على `main`، السطر الأول من `README.md` هو:
```
Versie: 1.0
```

وفي فرعك، غيّرته إلى:
```
Versie: 2.0
```

بينما في الفرع الآخر، يظهر:
```
Versie: 1.5
```

من على حق؟ Git لا يعرف. أنت تعرف.

---

## 2. كيف يبدو التعارض؟

يفتح Git الملف ويُدرج علامات:

```
<<<<<<< HEAD
Versie: 2.0
=======
Versie: 1.5
>>>>>>> فرع-آخر
```

- كل ما بين `<<<<<<< HEAD` و`=======` هو نسختك
- كل ما بين `=======` و`>>>>>>>` هو نسخة الفرع الآخر
- أنت من يقرر ما الذي سيبقى

---

## 3. حل التعارض: خطوة بخطوة

```bash
# تحاول الدمج
git merge فرع-آخر

# يُبلغك Git بالتالي: CONFLICT (content) in README.md
# افتح الملف في محرر النصوص الخاص بك
```

**في المحرر:**
1. ابحث عن علامات التعارض (`<<<<<<<`، `=======`، `>>>>>>>`)
2. قرر أي نسخة صحيحة — أو ادمجهما معًا
3. احذف جميع العلامات
4. احفظ الملف

**عودة إلى الطرفية:**
```bash
git add README.md
git commit -m "تم حل التعارض: تحديد رقم الإصدار إلى 2.0"
```

تم حل التعارض. وتم إنشاء commit الدمج.

---

## 4. تجنّب التعارضات

أفضل طريقة لتجنّب التعارضات: **التزامات (commits) وعمليات دمج صغيرة ومتكررة**.

كلما طال انتظارك قبل الدمج، زادت احتمالية أن يكون شخص آخر قد غيّر نفس الأسطر.

عادات جيدة:
- اجعل الفروع قصيرة العمر — اعمل بمقياس الأيام، لا الأسابيع
- اسحب (pull) بانتظام: `git pull origin main` على فرعك لتبقى محدَّثًا
- ناقشوا من يعمل على أي جزء

---

## 5. مراجعة الكود: الجودة قبل الدمج

**مراجعة الكود (code review)** تعني النظر في عمل شخص آخر قبل دمجه.

بصفتك مراجِعًا، انتبه إلى:
- هل التغيير مفهوم؟
- هل له عواقب غير متوقعة؟
- هل رسائل الـ commit واضحة؟
- هل هناك أخطاء إملائية أو تناقضات؟

بصفتك مختبِرًا (tester)، أنت بارع جدًا في المراجعة — فأنت تفكر أصلًا بالحالات الحدّية والمخاطر.

**آداب المراجعة الجيدة:**
- اطرح أسئلة بدلًا من فرض مطالب: "هل فكرت في...؟" بدلًا من "هذا خطأ."
- اذكر أيضًا ما هو جيد
- اترك غرورك خارج المراجعة — الأمر يتعلق بالمنتج

## 6. العلامات (Tags) والإصدارات (Releases)

**العلامة (tag)** هي اسم تمنحه لـ commit معيّن.
مفيدة لأرقام الإصدارات: `v1.0`، `v2.3.1`.

```bash
# إنشاء علامة خفيفة (lightweight tag)
git tag v1.0

# إنشاء علامة موثّقة (annotated tag، مع وصف)
git tag -a v1.0 -m "أول نسخة مستقرة"

# دفع العلامة إلى GitHub
git push origin v1.0
```

على GitHub، يمكنك إنشاء **إصدار (release)** من علامة معيّنة.
يحتوي الإصدار على:
- الكود في تلك اللحظة
- ملاحظات الإصدار (ما الجديد، وما الذي تم إصلاحه)
- مرفقات اختيارية (ملفات التثبيت)

بالنسبة للمختبِر، يُعتبر الإصدار نقطة انطلاق جولة اختبار جديدة.
