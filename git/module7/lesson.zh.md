# 模块7 — 冲突与质量

协作并不总是一帆风顺。
有时候，你想合并某些东西，Git会告诉你："这件事我一个人做不了。"
这不是错误——这是Git在向你提问。

---

## 1. 什么是合并冲突（merge conflict）？

当两个分支**以不同的方式修改了同一行**时，就会发生合并冲突。

Git自己无法决定哪个版本才是正确的。
它会标记出冲突的行，然后等待你的决定。

举例：在`main`上，`README.md`的第一行是：
```
Versie: 1.0
```

在你的分支上，你把它改成了：
```
Versie: 2.0
```

而在另一个分支上，写的是：
```
Versie: 1.5
```

谁是对的？Git不知道。但你知道。

---

## 2. 冲突长什么样？

Git会打开文件，插入以下标记：

```
<<<<<<< HEAD
Versie: 2.0
=======
Versie: 1.5
>>>>>>> 另一个分支
```

- `<<<<<<< HEAD` 和 `=======` 之间的内容，是你的版本
- `=======` 和 `>>>>>>>` 之间的内容，是另一个分支的版本
- 保留哪个，由你来决定

---

## 3. 解决冲突：一步一步来

```bash
# 你尝试进行合并
git merge 另一个分支

# Git会报告：CONFLICT (content) in README.md
# 在你的编辑器中打开这个文件
```

**在编辑器中：**
1. 找到冲突标记（`<<<<<<<`、`=======`、`>>>>>>>`）
2. 决定哪个版本是正确的——或者把两者结合起来
3. 删除所有标记
4. 保存文件

**回到终端：**
```bash
git add README.md
git commit -m "解决冲突：版本号定为2.0"
```

冲突已经解决了。合并提交（merge commit）也已经创建好了。

---

## 4. 预防冲突

避免冲突的最好方法是：**小而频繁的commit和合并**。

你等待合并的时间越长，别人改动同一行代码的可能性就越大。

好的习惯包括：
- 让分支的生命周期尽量短——以天为单位工作，而不是周
- 定期拉取：在你的分支上执行 `git pull origin main`，保持同步
- 和团队讨论清楚谁负责哪部分

---

## 5. 代码审查：合并之前的质量把关

**代码审查（code review）**指的是在别人的工作被合并之前，先查看一遍。

作为审查者，你需要关注：
- 这个改动容易理解吗？
- 它会不会带来意料之外的后果？
- commit信息写得清楚吗？
- 有没有拼写错误或不一致的地方？

作为一名测试人员，你天生就擅长做这件事——你早已习惯从边界情况和风险的角度去思考。

**良好的审查礼仪：**
- 用提问代替命令："你有没有考虑过……？" 而不是 "这是错的。"
- 也要指出做得好的地方
- 把自尊心留在审查之外——这关乎的是产品本身，不是个人

## 6. 标签（Tag）与发布（Release）

**标签（tag）**是你给某个特定commit起的名字。
对版本号很有用，比如：`v1.0`、`v2.3.1`。

```bash
# 创建一个轻量标签
git tag v1.0

# 创建一个带注释的标签（附带描述）
git tag -a v1.0 -m "第一个稳定版本"

# 把标签推送到GitHub
git push origin v1.0
```

在GitHub上，你可以基于某个标签创建一个**发布（release）**。
一个发布通常包含：
- 那个时间点的代码
- 发布说明（有哪些新功能，修复了什么问题）
- 可能还有附件（安装文件）

对测试人员来说，一个发布就是一轮测试的起点。
