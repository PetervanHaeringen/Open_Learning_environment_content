# الوحدة 8 — Git للمختبِرين (Testers)

بصفتك مختبِرًا، قد تستخدم Git بطريقة مختلفة عن المطوّر.
أنت تتعامل مع نصوص الاختبار (test scripts)، وتقارير الأخطاء، والملاحظات، والوثائق.
في هذه الوحدة، سترى كيف يدعم Git وGitHub عملك كمختبِر بشكل مباشر.

---

## 1. GitHub Issues: قلب سير العمل

**الـ issue** هو مهمة أو تقرير خطأ أو سؤال يتم تتبعه في GitHub.

بصفتك مختبِرًا، تُنشئ issues من أجل:
- الأخطاء التي وجدتها
- أسئلة اختبار موجَّهة إلى الفريق
- طلبات بيانات اختبار إضافية
- مقترحات لتحسين نصوص الاختبار

**تقرير خطأ جيد على شكل issue يحتوي على:**

```markdown
## الوصف
النقر على زر "حفظ" في النموذج يُظهر خطأ 500.

## خطوات إعادة الإنتاج
1. اذهب إلى /formulier
2. املأ جميع الحقول
3. انقر على "حفظ"

## السلوك المتوقَّع
يتم حفظ النموذج وتحصل على تأكيد.

## السلوك الفعلي
رسالة خطأ: Internal Server Error (500)

## البيئة
- المتصفح: Chrome 124
- نظام التشغيل: Windows 11
- بيئة الاختبار: staging
```

---

## 2. التصنيفات (Labels): إضافة تنظيم

تُستخدم التصنيفات (labels) لتصنيف الـ issues.
التصنيفات الافتراضية في GitHub:

| التصنيف | الاستخدام |
|-------|---------|
| `bug` | شيء لا يعمل كما هو متوقَّع |
| `enhancement` | مقترح تحسين |
| `question` | سؤال موجَّه إلى الفريق |
| `documentation` | الوثائق ناقصة أو غير صحيحة |
| `duplicate` | تم الإبلاغ عنه سابقًا |
| `won't fix` | قرار متعمَّد بعدم الإصلاح |

يمكنك أيضًا إنشاء تصنيفاتك الخاصة، مثل:
- `أولوية: عالية`
- `اختبار: انحدار (regression)`
- `بيئة: staging`

---

## 3. المعالم (Milestones): الربط بإصدار أو سبرنت

**المعلم (milestone)** يجمّع الـ issues التي تنتمي إلى إصدار أو سبرنت معيّن.

مثال:
- المعلم `Sprint 4 — Release 2.1`
- Issues: 12 خطأً، 3 طلبات اختبار
- التقدّم: 7 من أصل 15 مغلَقة

بصفتك مختبِرًا، يمنحك المعلم نظرة عامة: ما الذي يجب أن يكون جاهزًا قبل الإصدار؟

---

## 4. إدارة نصوص الاختبار في Git

نصوص الاختبار هي مجرد ملفات عادية (YAML، txt، Python، إلخ).
ولأنها موجودة في مستودع Git، تحصل على:

- **سجل تاريخي**: من غيّر نص الاختبار هذا، ومتى؟
- **العودة للخلف**: خطأ في نص اختبار؟ عد إلى النسخة السابقة.
- **التعاون**: يمكن لزميلك مراجعة نصوص الاختبار عبر طلب سحب (pull request).
- **إمكانية التتبع**: يمكنك ربط نص اختبار بـ issue معيّن.

**بنية مجلدات جيدة لنصوص الاختبار:**

```
testscripts/
  regressie/
    module1_login.yaml
    module2_formulieren.yaml
  smoke/
    dagelijkse_check.yaml
  exploratory/
    notities_sprint4.md
```

---

## 5. ربط تقرير خطأ بـ commit

في رسالة الـ commit، يمكنك الإشارة إلى issue معيّن:

```bash
git commit -m "إصلاح التحقق من تسجيل الدخول (#42)"
```

يتعرّف GitHub على `#42` وينشئ تلقائيًا رابطًا إلى issue رقم 42.
استخدم `Closes #42` لإغلاق الـ issue تلقائيًا عند الدمج:

```bash
git commit -m "إصلاح: زر الحفظ المعطّل في النموذج (Closes #58)"
```

---

## 6. سير عمل الاختبار في Git

الدورة النموذجية للمختبِر:

```
1. كتابة أو تعديل نص اختبار
       ↓
2. إنشاء فرع: test/sprint4-regressie
       ↓
3. التزامات (commits): تعديلات صغيرة برسائل واضحة
       ↓
4. طلب سحب (pull request) ← مراجعة من زميل
       ↓
5. تم العثور على خطأ؟ ← إنشاء issue مع خطوات إعادة الإنتاج
       ↓
6. تم إصلاح الخطأ من قِبَل المطوّر ← تختبر مرة أخرى على فرع الـ PR
       ↓
7. تم دمج الـ PR ← يتم تحديث المعلم (milestone)
```

Git ليس عملًا إداريًا إضافيًا.
إنه المكان الذي يصبح فيه عملك مرئيًا وقابلًا للتتبع.
