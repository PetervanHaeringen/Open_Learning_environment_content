# モジュール8 — テスターのためのGit

テスターであるあなたは、開発者とは少し違う形でGitを使うかもしれません。
あなたが扱うのは、テストスクリプト、バグレポート、発見事項、そしてドキュメントです。
このモジュールでは、GitとGitHubが、テスターとしてのあなたの仕事をどのように直接支えてくれるかを見ていきます。

---

## 1. GitHub Issue：作業プロセスの中心

**Issue（イシュー）**とは、GitHub上で管理されるタスク、バグ報告、あるいは質問のことです。

テスターであるあなたは、次のような場面でイシューを作成します：
- 見つけたバグ
- チームへのテストに関する質問
- 追加のテストデータのリクエスト
- テストスクリプトの改善提案

**良いバグレポート（イシューとして）には、次のような内容が含まれます：**

```markdown
## 説明
フォームの「保存」ボタンをクリックすると、500エラーが発生する。

## 再現手順
1. /formulier にアクセスする
2. すべての項目を入力する
3. 「保存」をクリックする

## 期待される動作
フォームが保存され、確認メッセージが表示される。

## 実際の動作
エラーメッセージ：Internal Server Error (500)

## 環境
- ブラウザ：Chrome 124
- OS：Windows 11
- テスト環境：staging
```

## 2. ラベル：構造を持たせる

ラベルはイシューを分類するために使います。
GitHubのデフォルトラベル：

| ラベル | 用途 |
|-------|---------|
| `bug` | 何かが期待通りに動作していない |
| `enhancement` | 改善提案 |
| `question` | チームへの質問 |
| `documentation` | ドキュメントが欠けている、または間違っている |
| `duplicate` | すでに報告済み |
| `won't fix` | あえて修正しないという判断 |

自分でラベルを作ることもできます：
- `優先度: 高`
- `テスト: リグレッション`
- `環境: staging`

---

## 3. マイルストーン：バージョンやスプリントとの紐づけ

**マイルストーン**とは、あるバージョンやスプリントに属するイシューをまとめたものです。

例：
- マイルストーン `Sprint 4 — Release 2.1`
- イシュー：バグ12件、テスト依頼3件
- 進捗：15件中7件がクローズ済み

テスターにとって、マイルストーンは全体像を把握する手がかりになります：リリースまでに何を終わらせておく必要があるか？

---

## 4. Gitでテストスクリプトを管理する

テストスクリプトは、ただの普通のファイルです（YAML、txt、Pythonなど）。
それらがGitリポジトリの中にあることで、次のようなメリットが得られます：

- **履歴**：このテストスクリプトを、誰が、いつ変更したか？
- **巻き戻し**：テストスクリプトにミスがあった？前のバージョンに戻せばいい。
- **共同作業**：同僚がプルリクエストを通じてテストスクリプトをレビューできる。
- **追跡可能性**：テストスクリプトをあるイシューと紐づけることができる。

**テストスクリプトのための良いフォルダ構成の例：**

```
testscripts/
  regressie/
    module1_login.yaml
    module2_formulieren.yaml
  smoke/
    dagelijkse_check.yaml
  exploratory/
    notities_sprint4.md
```

---

## 5. バグレポートをコミットに紐づける

コミットメッセージの中で、イシューを参照することができます：

```bash
git commit -m "ログイン検証を修正 (#42)"
```

GitHubは`#42`を認識し、自動的にイシュー42番へのリンクを作成します。
`Closes #42`を使うと、マージ時にそのイシューを自動的にクローズできます：

```bash
git commit -m "修正：フォームの保存ボタンが壊れていた問題 (Closes #58)"
```

---

## 6. Gitにおけるテストのワークフロー

テスターにとって典型的なサイクルは、次のようなものです：

```
1. テストスクリプトを書く、または調整する
       ↓
2. ブランチを作成する：test/sprint4-regressie
       ↓
3. コミット：わかりやすいメッセージをつけた小さな変更
       ↓
4. プルリクエスト → 同僚によるレビュー
       ↓
5. バグを発見？ → 再現手順つきのイシューを作成する
       ↓
6. 開発者がバグを修正 → あなたがPRブランチで再テストする
       ↓
7. PRがマージされる → マイルストーンが更新される
```

Gitは、余計な事務作業ではありません。
それは、あなたの仕事が目に見える形になり、追跡できるようになる場所なのです。
