# 모듈 8 — 테스터를 위한 Git

테스터인 당신은 개발자와는 조금 다르게 Git을 사용할 수도 있습니다.
당신은 테스트 스크립트, 버그 리포트, 발견 사항, 그리고 문서를 다룹니다.
이 모듈에서는 Git과 GitHub가 테스터로서 당신의 작업을 어떻게 직접적으로 뒷받침해 주는지 살펴봅니다.

---

## 1. GitHub 이슈: 작업 흐름의 중심

**이슈(issue)**란 GitHub에서 추적되는 작업, 버그 리포트, 또는 질문을 말합니다.

테스터로서 당신은 다음과 같은 경우에 이슈를 만듭니다:
- 발견한 버그
- 팀에게 던지는 테스트 관련 질문
- 추가 테스트 데이터 요청
- 테스트 스크립트에 대한 개선 제안

**좋은 버그 리포트(이슈)는 다음을 포함합니다:**

```markdown
## 설명
폼에서 "저장" 버튼을 클릭하면 500 오류가 발생합니다.

## 재현 단계
1. /formulier로 이동합니다
2. 모든 항목을 입력합니다
3. "저장"을 클릭합니다

## 예상 동작
폼이 저장되고 확인 메시지가 표시됩니다.

## 실제 동작
오류 메시지: Internal Server Error (500)

## 환경
- 브라우저: Chrome 124
- OS: Windows 11
- 테스트 환경: staging
```

---

## 2. 라벨(Labels): 구조를 부여하기

라벨은 이슈를 분류하는 데 사용됩니다.
GitHub의 기본 라벨:

| 라벨 | 용도 |
|-------|---------|
| `bug` | 무언가가 예상대로 작동하지 않음 |
| `enhancement` | 개선 제안 |
| `question` | 팀에 대한 질문 |
| `documentation` | 문서가 없거나 잘못됨 |
| `duplicate` | 이미 이전에 보고됨 |
| `won't fix` | 의도적으로 수정하지 않기로 한 결정 |

자신만의 라벨을 만들 수도 있습니다:
- `우선순위: 높음`
- `테스트: 회귀`
- `환경: staging`

---

## 3. 마일스톤: 버전이나 스프린트와 연결하기

**마일스톤(milestone)**은 특정 버전이나 스프린트에 속하는 이슈들을 그룹으로 묶은 것입니다.

예시:
- 마일스톤 `Sprint 4 — Release 2.1`
- 이슈: 버그 12개, 테스트 요청 3개
- 진행 상황: 15개 중 7개 완료

테스터에게 마일스톤은 전체적인 그림을 보여줍니다: 릴리스 전까지 무엇이 준비되어야 하는가?

---

## 4. Git에서 테스트 스크립트 관리하기

테스트 스크립트는 그저 평범한 파일들입니다(YAML, txt, Python 등).
이것들이 Git 저장소 안에 있기 때문에, 당신은 다음을 얻게 됩니다:

- **이력**: 이 테스트 스크립트를 누가, 언제 수정했는가?
- **되돌리기**: 테스트 스크립트에 실수가 있었다면? 이전 버전으로 돌아가면 됩니다.
- **협업**: 동료가 풀 리퀘스트를 통해 테스트 스크립트를 리뷰할 수 있습니다.
- **추적 가능성**: 테스트 스크립트를 특정 이슈와 연결할 수 있습니다.

**테스트 스크립트를 위한 좋은 폴더 구조:**

```
testscripts/
  regressie/
    module1_login.yaml
    module2_formulieren.yaml
  smoke/
    dagelijkse_check.yaml
  exploratory/
    notities_sprint4.md
```

---

## 5. 버그 리포트를 커밋과 연결하기

커밋 메시지 안에서 이슈를 참조할 수 있습니다:

```bash
git commit -m "로그인 유효성 검사 수정 (#42)"
```

GitHub는 `#42`를 인식해서 자동으로 42번 이슈로 연결되는 링크를 만듭니다.
`Closes #42`를 사용하면 병합 시 해당 이슈를 자동으로 닫을 수 있습니다:

```bash
git commit -m "수정: 폼의 고장난 저장 버튼 (Closes #58)"
```

---

## 6. Git에서의 테스트 워크플로우

테스터의 전형적인 작업 흐름은 다음과 같습니다:

```
1. 테스트 스크립트를 작성하거나 수정하기
       ↓
2. 브랜치 만들기: test/sprint4-regressie
       ↓
3. 커밋: 명확한 메시지와 함께하는 작은 변경들
       ↓
4. 풀 리퀘스트 → 동료의 리뷰
       ↓
5. 버그를 발견했나요? → 재현 단계를 포함한 이슈 만들기
       ↓
6. 개발자가 버그를 수정함 → 당신이 PR 브랜치에서 다시 테스트함
       ↓
7. PR이 병합됨 → 마일스톤이 업데이트됨
```

Git은 부가적인 행정 업무가 아닙니다.
그것은 당신의 작업이 눈에 보이고, 추적 가능해지는 장소입니다.
