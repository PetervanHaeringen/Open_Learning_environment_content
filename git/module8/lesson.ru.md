# Модуль 8 — Git для тестировщиков

Как тестировщик, вы можете использовать Git иначе, чем разработчик.
Вы работаете с тестовыми скриптами, отчётами об ошибках, находками и документацией.
В этом модуле вы увидите, как Git и GitHub напрямую поддерживают вашу работу как тестировщика.

---

## 1. GitHub Issues: сердце рабочего процесса

**Issue** — это задача, отчёт об ошибке или вопрос, которые отслеживаются в GitHub.

Как тестировщик, вы создаёте issue для:
- найденных багов
- вопросов по тестированию к команде
- запросов на дополнительные тестовые данные
- предложений по улучшению тестовых скриптов

**Хороший отчёт об ошибке в виде issue содержит:**

```markdown
## Описание
Клик по кнопке «Сохранить» в форме выдаёт ошибку 500.

## Шаги для воспроизведения
1. Перейдите на /formulier
2. Заполните все поля
3. Нажмите «Сохранить»

## Ожидаемое поведение
Форма сохраняется, и вы получаете подтверждение.

## Фактическое поведение
Сообщение об ошибке: Internal Server Error (500)

## Окружение
- Браузер: Chrome 124
- ОС: Windows 11
- Тестовое окружение: staging
```

## 2. Метки (labels): добавление структуры

Метки категоризируют issue.
Метки по умолчанию в GitHub:

| Метка | Использование |
|-------|---------|
| `bug` | Что-то работает не так, как ожидалось |
| `enhancement` | Предложение по улучшению |
| `question` | Вопрос к команде |
| `documentation` | Документация отсутствует или неверна |
| `duplicate` | Уже сообщалось ранее |
| `won't fix` | Осознанное решение не исправлять |

Вы также можете создавать собственные метки:
- `приоритет: высокий`
- `тест: регрессия`
- `окружение: staging`

---

## 3. Вехи (milestones): привязка к версии или спринту

**Веха (milestone)** группирует issue, относящиеся к определённой версии или спринту.

Пример:
- Веха `Sprint 4 — Release 2.1`
- Issue: 12 багов, 3 запроса на тестирование
- Прогресс: 7 из 15 закрыто

Как тестировщику, веха даёт вам обзор: что должно быть готово перед релизом?

---

## 4. Управление тестовыми скриптами в Git

Тестовые скрипты — это обычные файлы (YAML, txt, Python и т. д.).
Поскольку они хранятся в Git-репозитории, вы получаете:

- **Историю**: кто и когда изменил этот тестовый скрипт?
- **Откат**: ошибка в тестовом скрипте? Вернитесь к предыдущей версии.
- **Совместную работу**: коллега может проверить тестовые скрипты через пул-реквест.
- **Прослеживаемость**: вы можете связать тестовый скрипт с issue.

**Хорошая структура папок для тестовых скриптов:**

```
testscripts/
  regressie/
    module1_login.yaml
    module2_formulieren.yaml
  smoke/
    dagelijkse_check.yaml
  exploratory/
    notities_sprint4.md
```

## 5. Связывание отчёта об ошибке с коммитом

В сообщении коммита можно сослаться на issue:

```bash
git commit -m "Исправлена валидация логина (#42)"
```

GitHub распознаёт `#42` и автоматически создаёт ссылку на issue 42.
Используйте `Closes #42`, чтобы автоматически закрыть issue при слиянии:

```bash
git commit -m "Исправление: сломанная кнопка сохранения в форме (Closes #58)"
```

## 6. Рабочий процесс тестирования в Git

Типичный цикл для тестировщика:

```
1. Написать или изменить тестовый скрипт
       ↓
2. Создать ветку: test/sprint4-regressie
       ↓
3. Коммиты: небольшие изменения с понятными сообщениями
       ↓
4. Пул-реквест → ревью от коллеги
       ↓
5. Найден баг? → Создать issue с шагами воспроизведения
       ↓
6. Баг исправлен разработчиком → вы снова тестируете в ветке PR
       ↓
7. PR слит → веха обновлена
```

Git — это не дополнительная бюрократия.
Это место, где ваша работа становится видимой и прослеживаемой.
