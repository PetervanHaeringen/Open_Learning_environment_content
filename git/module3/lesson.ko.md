# 모듈 3 — 그림으로 보는 버전 관리

명령어를 입력하기 전에, 그것을 *볼 수 있어야* 합니다.
이 모듈에서는 머릿속 모델을 만들어 갑니다. Git을 그림으로 그리면 어떤 모습일까요?

---

## 1. 타임라인: 일렬로 늘어선 커밋

Git의 가장 단순한 상태는 커밋이 일직선으로 늘어선 형태입니다.
각각의 커밋은 스냅샷이며, 각각이 자신의 이전 커밋을 가리킵니다.

```
○ — ○ — ○ — ○ — ○
A   B   C   D   E
```

- **A**는 첫 번째 커밋(시작점)
- **E**는 가장 최근의 커밋(현재 상태)
- 화살표는 과거를 가리킵니다

타임라인은 왼쪽에서 오른쪽으로 읽습니다. 이것이 역사가 자라온 순서입니다.

![Git 타임라인——일렬로 늘어선 커밋](images/tijdlijn_lineair.png)

## 2. 브랜치: 옆으로 뻗어나가는 길

상상해 보세요. 당신은 본류를 건드리지 않고 무언가를 시도하고 싶습니다.
그래서 **브랜치**를 만듭니다——기존 커밋에서 시작하는, 옆으로 뻗어나가는 길입니다.

```
○ — ○ — ○ — ○ — ○       (main)
              |
              ○ — ○       (experiment)
```

- `main`은 그대로 계속 진행됩니다
- `experiment`는 커밋 D에서 시작하여 독립적으로 자랍니다
- 둘 다 동시에 존재하며, 서로에게 영향을 주지 않습니다

Git에서 브랜치란, 어떤 커밋을 가리키는 이름에 불과합니다.
그것뿐입니다. 파일의 복사본도 없고, 중복된 폴더도 없습니다——그저 라벨일 뿐입니다.

![타임라인에서 갈라져 나온 브랜치](images/branch_zijtak.png)

---

## 3. 머지: 두 브랜치를 합치기

실험이 끝나면, 그것을 `main`으로 되돌리고 싶어집니다.
이것을 **머지(merge)**라고 합니다.

```
○ — ○ — ○ — ○ — ○ — ○   (main, 머지 후)
              |       |
              ○ — ○ ——   (experiment, 머지됨)
```

Git은 공통의 조상(커밋 D)과 두 끝단을 비교합니다.
그리고 변경 내용을 조합하여 새로운 **머지 커밋**을 만듭니다(main의 마지막 ○).

만약 같은 줄이 두 브랜치 모두에서 변경되었다면 → 충돌(conflict)이 발생합니다.
그렇지 않다면 → 자동으로 머지됩니다.

![두 브랜치의 머지](images/merge_visueel.png)

## 4. HEAD: 당신은 지금 여기에 있습니다

`HEAD`는 당신이 지금 그래프의 어디에 있는지를 보여주는 스티커 같은 것입니다.

```
○ — ○ — ○ — ○ — ○
                 ↑
                HEAD (main)
```

다른 브랜치로 전환하면(`git switch experiment`), 이 스티커도 함께 이동합니다.

```
○ — ○ — ○ — ○ — ○       (main)
              |
              ○ — ○
                   ↑
                  HEAD (experiment)
```

지금 당신이 커밋하는 모든 것은 HEAD가 가리키는 브랜치로 들어갑니다.

---

## 5. 과거로 돌아가기

예를 들어, 커밋 C에 지금 조사하고 싶은 버그가 포함되어 있다고 합시다.
일시적으로 HEAD를 C로 이동시킬 수 있습니다(`git checkout C`).

```
○ — ○ — ○ — ○ — ○
         ↑
        HEAD (detached)
```

그러면 파일은 그 시점의 상태 그대로 보입니다.
Git은 이것을 "detached HEAD(분리된 HEAD)"라고 부릅니다——당신은 브랜치 위가 아니라 커밋 위에 직접 서 있는 상태입니다.

보는 것만으로는 유용합니다. 하지만 새로운 브랜치를 만들지 않고 커밋하는 것은 위험합니다.

---

## 6. 연습: 직접 그려보기

펜과 종이를 준비하세요.

1. 5개의 원(커밋 A~E)으로 일직선을 그립니다.
2. C에서 시작하는 브랜치를 그리고, 거기에 2개의 커밋을 더 추가합니다.
3. E 뒤에 본류로 돌아오는 머지를 그립니다.
4. HEAD 스티커를 올바른 위치에 붙입니다.

이 그림이 바로 Git이 내부에서 실제로 관리하고 있는 내용입니다.
