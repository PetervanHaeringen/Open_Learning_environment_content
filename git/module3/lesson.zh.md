# 模块3 — 用图像理解版本控制

在你输入命令之前，你需要先能*看见*它。
本模块将帮你建立心智模型：如果把Git画出来，它会是什么样子？

---

## 1. 时间线：一排提交

Git中最简单的情况，是一条由提交（commit）组成的直线。
每个commit都是一个快照，每个commit都指向它的前一个。

```
○ — ○ — ○ — ○ — ○
A   B   C   D   E
```

- **A** 是第一个commit（起点）
- **E** 是最新的commit（当前状态）
- 箭头指向过去

从左到右阅读这条时间线：这就是历史增长的方式。

![Git时间线——一排提交](images/tijdlijn_lineair.png)

## 2. 分支（branch）：一条支线

想象一下：你想尝试一些新东西，但又不想影响主线。
于是你创建一个**分支**——一条从已有commit开始的支线。

```
○ — ○ — ○ — ○ — ○       (main)
              |
              ○ — ○       (experiment)
```

- `main` 继续正常前进
- `experiment` 从commit D开始，独立发展
- 两者同时存在，互不影响

在Git中，分支其实只是一个指向某个commit的名字。
仅此而已。没有文件的复制，没有重复的文件夹——只是一个标签。

![分支作为时间线的支线](images/branch_zijtak.png)

## 3. 合并（merge）：把两个分支合到一起

当实验完成后，你想把它合并回`main`。
这个操作叫做**merge**（合并）。

```
○ — ○ — ○ — ○ — ○ — ○   (main, 合并后)
              |       |
              ○ — ○ ——   (experiment, 已合并)
```

Git会查看共同的祖先提交（commit D）以及两个分支的末端。
它会合并这些变化，并创建一个新的**合并提交（merge commit）**（main上最后的那个○）。

如果两个分支修改了相同的代码行 → 产生冲突。
如果没有 → 自动合并。

![两个分支的合并](images/merge_visueel.png)

## 4. HEAD：你现在在这里

`HEAD` 就像一个贴纸，标示出你现在在图中的位置。

```
○ — ○ — ○ — ○ — ○
                 ↑
                HEAD (main)
```

当你切换到另一个分支时（`git switch experiment`），这个贴纸也会跟着移动：

```
○ — ○ — ○ — ○ — ○       (main)
              |
              ○ — ○
                   ↑
                  HEAD (experiment)
```

你现在提交的任何内容，都会进入HEAD所在的那个分支。

---

## 5. 回到过去

假设commit C包含一个你现在想调查的错误。
你可以临时把HEAD移动到C（`git checkout C`）。

```
○ — ○ — ○ — ○ — ○
         ↑
        HEAD (detached)
```

这时你的文件会呈现出那个时刻的样子。
Git把这种状态称为"detached HEAD"（分离头指针）——你此时不在某个分支上，而是直接停留在某个commit上。

用来查看很有用。但如果在这种状态下提交而不先创建新分支，就会有风险。

## 6. 练习：自己动手画一画

拿一支笔和一张纸。

1. 画一条直线，上面有五个圆圈（commit A到E）。
2. 画一条从C开始的分支，再加两个commit。
3. 画一个合并，在E之后合回主线。
4. 把HEAD贴纸放在正确的位置上。

这幅图正是Git内部实际记录的内容。
