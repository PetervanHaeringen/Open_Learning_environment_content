# モジュール4 — Gitゲーム

Gitは、実際に*体で感じて*みて初めて、本当に理解できるものです。
このゲームでは、グループそのものがバージョン管理システムになります。
ターミナルもコマンドも使いません。しかし、Gitの内部で何が起きているのかを、実際に体験できます。

---

## 用意するもの

- 付箋またはカード（最低30枚）
- マーカー（最低2色）
- 「タイムライン」として使うテーブルまたは壁
- 線を引くためのテープ（マスキングテープなど）1巻
- 参加人数：3〜8人

---

## 役割

| 役割 | 仕事 |
|-----|------|
| **Maintainer（メンテナー）** | `main`ブランチを管理する。マージを承認する。 |
| **Developer A（開発者A）** | 自分のブランチで作業する。 |
| **Developer B（開発者B）** | 別のブランチで作業する（Aと同時進行）。 |
| **Reviewer（レビュアー）** | ブランチがマージされる前にそれを確認する。 |

少人数のグループでは、一人が複数の役割を兼任してもかまいません。

---

## 「プロジェクト」

このプロジェクトは、架空のテキストファイル `README.txt` です。
最初のバージョンは3行から成ります：

```
Projectnaam: Git Garden
Versie: 1.0
Beschrijving: Een oefenproject.
```

この最初のバージョンを付箋に書きましょう。これが**コミットA**——起点です。
それをタイムラインの左端に貼ります。

---

## ラウンド1 — 直線のタイムライン

**目的：** コミットが次々と連なっていく様子を体験する。

1. Developer Aが新しい付箋に小さな変更を書きます。
   例：`Versie: 1.1`
   上に次のように書きます：`Commit B — Developer A — 「バージョンを更新」`
2. コミットBをAの右側に貼り、矢印でつなぎます。
3. Developer Aがさらに変更を加えます → コミットC。
4. Developer Bも同じことをします → コミットD、E。

5回コミットすると、タイムラインができあがります。話し合ってみましょう：
- 誰が何を変えたか？
- コミットBに戻ることはできるか？

---

## ラウンド2 — ブランチを作る

**目的：** 2人が同時に同じプロジェクトに取り組めることを体験する。

1. テープを使って、コミットCから2本の線を引きます——1本は上へ、もう1本はそのまま直進させます。
2. Developer Aは上の線で作業を続けます：コミットD（自分のファイルのバージョン）。
3. Developer Bは下の線で作業します：コミットD'（自分のバージョン——別の変更内容）。
4. 2人とも自分の付箋を書き、自分の線に貼ります。

これで2つのブランチができました。話し合ってみましょう：
- A側の線には何が書かれているか？B側の線には何が書かれているか？
- 両方とも有効なのか？——はい。Gitは両方を記録しています。

---

## ラウンド3 — マージする

**目的：** マージとは何か、そしてどんなときにうまくいかなくなるのかを体験する。

**シナリオA：コンフリクトなし**
Developer Aは説明文を変更しました。
Developer Bはバージョン番号を変更しました。
→ コンフリクトなし。Reviewerは両方の変更を新しい付箋にまとめます：**マージコミットM**。
Mを2本の線の右側に貼り、そこに向かう矢印を2本引きます。

**シナリオB：コンフリクトあり**
Developer Aは `Versie: 2.0` と書きました。
Developer Bも `Versie: 1.5` と書きました。
→ コンフリクト（衝突）です！同じ行に、2つの異なる値が入っています。
Reviewerは作業を止めます。話し合ってみましょう：どちらが正しいか？どちらを選ぶか？
その決定をマージコミットに書きます。

これはまさにGitがやっていることです：可能なときは自動的にマージし、できないときは止まります。

---

## ラウンド4 — 過去に戻る

**目的：** Gitは何も忘れないということを理解する。

1. タイムラインを見てください。
2. Maintainerが尋ねます：「コミットBの時点で、このファイルはどんな状態だった？」
3. 全員がコミットBの付箋を見れば——答えを出すことができます。

Gitがしているのは、まさにこれです：すべてのコミットに、プロジェクトの完全な状態が含まれています。
いつでも過去に戻ることができます。

---

## ふりかえり

グループで話し合ってみましょう：

1. このゲームの中で、一番難しかった瞬間はどこでしたか？
2. コンフリクトはいつ発生し、どのように解決しましたか？
3. もっと良いコミットメッセージがあったとしたら、どんなものでしたか？
4. これは、あなたが日常的にファイルを扱う仕事とどう関係していますか？

---

## 本物のターミナルとのつながり

このゲームを終えたあなたは、これらの概念を内側から理解しています：

| ゲームの中でやったこと | Gitコマンド |
|--------------------------|--------------|
| 付箋を書く（変更を記録する） | `git commit -m "..."` |
| 新しい線を引く（ブランチを作る） | `git branch 名前` |
| 別の線に切り替える | `git switch 名前` |
| 2本の線を1つにまとめる | `git merge 名前` |
| 以前の付箋を振り返る | `git log` / `git checkout` |

次のモジュールでは、まさにこれを——今度はターミナルの中で——実際に行います。
