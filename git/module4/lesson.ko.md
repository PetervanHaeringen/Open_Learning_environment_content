# 모듈 4 — Git 게임

Git은 직접 *느껴봐야만* 진짜로 이해할 수 있습니다.
이 게임에서는 그룹 전체가 버전 관리 시스템이 됩니다.
터미널도 없고, 명령어도 없습니다. 하지만 Git 내부에서 무슨 일이 일어나는지 실제로 체험하게 됩니다.

---

## 준비물

- 포스트잇 또는 카드 (최소 30장)
- 마커펜 (최소 2가지 색)
- "타임라인"으로 사용할 테이블이나 벽
- 선을 그릴 테이프 또는 마스킹 테이프 1롤
- 참가자: 3~8명

---

## 역할

| 역할 | 임무 |
|-----|------|
| **Maintainer(관리자)** | `main` 브랜치를 관리합니다. 머지를 승인합니다. |
| **Developer A(개발자 A)** | 자신의 브랜치에서 작업합니다. |
| **Developer B(개발자 B)** | 다른 브랜치에서 작업합니다(A와 동시에). |
| **Reviewer(리뷰어)** | 머지되기 전에 브랜치를 검토합니다. |

소규모 그룹에서는 한 사람이 여러 역할을 맡을 수 있습니다.

---

## "프로젝트"

프로젝트는 가상의 텍스트 파일입니다: `README.txt`
초기 버전은 세 줄로 되어 있습니다:

```
Projectnaam: Git Garden
Versie: 1.0
Beschrijving: Een oefenproject.
```

이 초기 버전을 포스트잇에 적으세요. 이것이 **커밋 A** — 시작점입니다.
타임라인의 왼쪽 끝에 붙이세요.

---

## 1라운드 — 일직선 타임라인

**목표:** 커밋이 어떻게 연이어 이어지는지 체험하기.

1. Developer A가 새 포스트잇에 작은 변경 사항을 적습니다.
   예: `Versie: 1.1`
   위쪽에 다음과 같이 적습니다: `Commit B — Developer A — "버전 업데이트"`
2. 커밋 B를 A의 오른쪽에 붙이고, 화살표로 연결합니다.
3. Developer A가 또 다른 변경을 합니다 → 커밋 C.
4. Developer B도 같은 방식으로 합니다 → 커밋 D, E.

다섯 번의 커밋 후, 하나의 타임라인이 완성됩니다. 이야기해 보세요:
- 누가 무엇을 바꿨나요?
- 커밋 B로 돌아갈 수 있나요?

---

## 2라운드 — 브랜치 만들기

**목표:** 두 사람이 동시에 같은 프로젝트에서 작업할 수 있다는 것을 체험하기.

1. 테이프로 커밋 C에서 시작하는 두 줄을 그립니다 — 하나는 위로, 하나는 그대로 직진.
2. Developer A는 위쪽 줄에서 계속 작업합니다: 커밋 D(자신의 파일 버전).
3. Developer B는 아래쪽 줄에서 작업합니다: 커밋 D'(자신의 버전 — 다른 변경 사항).
4. 둘 다 자신의 포스트잇을 적고, 자신의 줄에 붙입니다.

이제 두 개의 브랜치가 생겼습니다. 이야기해 보세요:
- A 줄에는 무엇이 적혀 있나요? B 줄에는요?
- 둘 다 유효한가요? 네. Git은 둘 다 기록합니다.

---

## 3라운드 — 머지하기

**목표:** 머지가 무엇인지, 그리고 언제 잘못될 수 있는지 체험하기.

**시나리오 A: 충돌 없음**
Developer A가 설명을 바꿨습니다.
Developer B가 버전을 바꿨습니다.
→ 충돌 없음. Reviewer가 두 변경 사항을 새 포스트잇에 합칩니다: **머지 커밋 M**.
M을 두 줄의 오른쪽에 붙이고, M을 향한 화살표 두 개를 그립니다.

**시나리오 B: 충돌 발생**
Developer A는 이렇게 적습니다: `Versie: 2.0`
Developer B도 이렇게 적습니다: `Versie: 1.5`
→ 충돌입니다! 같은 줄에, 서로 다른 두 값.
Reviewer는 멈춥니다. 이야기해 보세요: 누가 맞나요? 무엇을 선택할 건가요?
그 결정을 머지 커밋에 적으세요.

이것이 바로 Git이 하는 일입니다: 가능하면 자동으로 머지하고, 불가능하면 멈춥니다.

---

## 4라운드 — 과거로 돌아가기

**목표:** Git이 아무것도 잊지 않는다는 것을 이해하기.

1. 타임라인을 보세요.
2. Maintainer가 묻습니다: "커밋 B 시점에 파일이 어떤 모습이었나요?"
3. 모두가 커밋 B의 포스트잇을 보면 — 답을 알 수 있습니다.

Git이 하는 일이 바로 이것입니다: 모든 커밋은 프로젝트의 완전한 상태를 담고 있습니다.
언제든지 과거로 돌아갈 수 있습니다.

---

## 마무리 토론

그룹과 함께 이야기해 보세요:

1. 게임에서 가장 어려웠던 순간은 언제였나요?
2. 충돌은 언제 발생했고, 어떻게 해결했나요?
3. 더 나은 커밋 메시지는 무엇이었을까요?
4. 이것이 여러분의 일상적인 파일 작업과 어떤 관련이 있나요?

## 실제 터미널과의 연결

이 게임을 마친 후에는 이 개념들을 속속들이 알게 됩니다:

| 게임에서 한 일 | Git 명령어 |
|--------------------------|--------------|
| 포스트잇 적기 (변경 사항 기록하기) | `git commit -m "..."` |
| 새 줄 그리기 (브랜치 만들기) | `git branch 이름` |
| 다른 줄로 전환하기 | `git switch 이름` |
| 두 줄 합치기 | `git merge 이름` |
| 이전 포스트잇 돌아보기 | `git log` / `git checkout` |

다음 모듈에서는 바로 이것을 — 이번엔 터미널에서 — 직접 해볼 것입니다.
