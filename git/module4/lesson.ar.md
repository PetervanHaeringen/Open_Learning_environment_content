# الوحدة 4 — لعبة Git

لن تفهم Git حقًا إلا بعد أن *تشعر* به.
في هذه اللعبة، تتحول المجموعة نفسها إلى نظام للتحكم بالإصدارات.
لا طرفية (terminal). لا أوامر. لكن تجربة حقيقية لما يحدث بالفعل داخل Git.

---

## المواد اللازمة

- أوراق لاصقة (post-its) أو بطاقات (30 على الأقل)
- أقلام تحديد (لونان على الأقل)
- طاولة أو حائط يُستخدم كـ"خط زمني"
- بكرة شريط لاصق أو شريط رسام لرسم الخطوط
- المشاركون: من 3 إلى 8 أشخاص

---

## الأدوار

| الدور | المهمة |
|-----|------|
| **Maintainer (المشرف)** | يدير فرع `main`. يوافق على عمليات الدمج (merges). |
| **Developer A (المطوّر أ)** | يعمل على فرعه الخاص. |
| **Developer B (المطوّر ب)** | يعمل على فرع آخر (في نفس وقت المطوّر أ). |
| **Reviewer (المراجِع)** | يراجع الفروع قبل دمجها. |

في المجموعات الصغيرة، يمكن لشخص واحد أن يتولى أكثر من دور.

---

## "المشروع"

المشروع عبارة عن ملف نصي وهمي: `README.txt`
النسخة الأولية تحتوي على ثلاثة أسطر:

```
Projectnaam: Git Garden
Versie: 1.0
Beschrijving: Een oefenproject.
```

اكتب هذه النسخة الأولية على ورقة لاصقة. هذا هو **commit A** — نقطة البداية.
الصقها في أقصى يسار الخط الزمني.

---

## الجولة 1 — خط زمني مستقيم

**الهدف:** تجربة كيف تتوالى الالتزامات (commits) واحدًا تلو الآخر.

1. يكتب Developer A تغييرًا صغيرًا على ورقة لاصقة جديدة.
   مثال: `Versie: 1.1`
   اكتب في الأعلى: `Commit B — Developer A — "تم تحديث الإصدار"`
2. الصق commit B إلى يمين A، وصله بسهم.
3. يقوم Developer A بتغيير آخر ← commit C.
4. يفعل Developer B الشيء نفسه ← commit D، E.

بعد خمسة commits، سيكون لديكم خط زمني. ناقشوا:
- من غيّر ماذا؟
- هل يمكنكم العودة إلى commit B؟

---

## الجولة 2 — التفريع (branching)

**الهدف:** تجربة أن شخصين يمكنهما العمل على نفس المشروع في نفس الوقت.

1. باستخدام الشريط اللاصق، ارسموا خطين ينطلقان من commit C — واحد للأعلى، والآخر مستقيم.
2. يواصل Developer A العمل على الخط العلوي: commit D (نسخته من الملف).
3. يعمل Developer B على الخط السفلي: commit D' (نسخته — تغييرات مختلفة).
4. يكتب كلاهما ورقاتهما اللاصقة، ويلصقانها على خطهما الخاص.

الآن أصبح لديكم فرعان. ناقشوا:
- ماذا يوجد على خط A؟ وماذا على خط B؟
- هل كلاهما صحيح؟ نعم. يحتفظ Git بكليهما.

---

## الجولة 3 — الدمج (merge)

**الهدف:** تجربة معنى الدمج — ومتى يمكن أن يسوء الأمر.

**السيناريو أ: لا يوجد تعارض**
غيّر Developer A الوصف.
غيّر Developer B الإصدار.
← لا يوجد تعارض. يقوم Reviewer بدمج كلا التغييرين في ورقة لاصقة جديدة: **commit دمج M**.
الصق M إلى يمين الخطين، مع سهمين يشيران إليه.

**السيناريو ب: يوجد تعارض**
يكتب Developer A: `Versie: 2.0`
ويكتب Developer B أيضًا: `Versie: 1.5`
← تعارض! نفس السطر، قيمتان مختلفتان.
يتوقف Reviewer. ناقشوا: من على حق؟ ماذا تختارون؟
اكتبوا القرار على commit الدمج.

هذا بالضبط ما يفعله Git: يدمج تلقائيًا عندما يستطيع، ويتوقف عندما لا يستطيع.

---

## الجولة 4 — العودة بالزمن

**الهدف:** فهم أن Git لا ينسى أي شيء أبدًا.

1. انظروا إلى الخط الزمني.
2. يسأل Maintainer: "كيف كان شكل الملف عند commit B؟"
3. ينظر الجميع إلى ورقة commit B اللاصقة — ويمكنهم تقديم الإجابة.

هذا بالضبط ما يفعله Git: كل commit يحتوي على الحالة الكاملة للمشروع.
يمكنك دائمًا العودة إليه.

---

## نقاش ختامي

ناقشوا مع المجموعة:

1. ما كانت أصعب لحظة في اللعبة؟
2. متى نشأ التعارض — وكيف حللتموه؟
3. ما الذي كان يمكن أن يكون رسالة commit أفضل؟
4. كيف يرتبط هذا بعملكم اليومي مع الملفات؟

---

## الربط مع الطرفية الحقيقية

بعد هذه اللعبة، أصبحتم تعرفون المفاهيم من الداخل:

| ما فعلتموه في اللعبة | أمر Git |
|--------------------------|--------------|
| كتابة ورقة لاصقة (تسجيل تغيير) | `git commit -m "..."` |
| رسم خط جديد (إنشاء فرع) | `git branch الاسم` |
| الانتقال إلى خط آخر | `git switch الاسم` |
| دمج خطين معًا | `git merge الاسم` |
| النظر إلى ورقة لاصقة سابقة | `git log` / `git checkout` |

في الوحدة التالية، ستقومون بهذا بالضبط — لكن في الطرفية هذه المرة.
