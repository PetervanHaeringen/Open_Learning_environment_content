# Module 6 – Bug Reporting

Bug reporting is one of the most important skills a tester has.

A good bug report is:
- clear
- reproducible
- complete
- usable for developers

In this module you'll learn how to write professional bug reports.

---

## 1. What is a bug?

A **bug** is a situation where software doesn't do what's expected.

That can involve:

- functional errors
- layout problems
- incorrect error messages
- unexpected behavior
- security issues
- performance problems

A bug is therefore the gap between:

> expected behavior ↔ actual behavior

---

## 2. What makes a good bug report?

A good bug report is:

- **Clear** — everyone understands the problem
- **Reproducible** — someone else can make it happen again
- **Complete** — all relevant information is included
- **Neutral** — factual, without blame or emotion

### Example

#### Bad bug report

> "The site doesn't work. Fix pls."

#### Good bug report

> "Clicking 'Save' produces a 500 error, and the form doesn't get saved."

---

## 3. Severity and Priority

Testers often attach labels to bugs.

### Severity

How serious is the problem for the system?

### Priority

How quickly does it need to be fixed?

### Examples

#### High severity, low priority
A crash in a feature almost nobody uses.

#### Low severity, high priority
A spelling mistake on an important client's homepage.

---

## 4. Bug Report Template

Use this template when writing bug reports.

```text
Title:
  Short and clear description

Environment:
  Browser, OS, version, device

Severity:
Priority:

Steps to reproduce:
  1. ...
  2. ...
  3. ...

Expected result:
  What should happen?

Actual result:
  What happened instead?

Screenshot / log:
  (optional but recommended)

Additional notes:
  frequency, impact, particulars
```

## 5. Practical assignment: write 3 bug reports

You're now going to write three bug reports based on issues you found earlier during exploratory testing.

### Assignment

1. Choose three issues from your session report.
2. Write a full bug report for each issue.
3. Use the template above.
4. Check whether the bug is reproducible.
5. Have a classmate test your report.

> A bug report is only good once someone else can reproduce the exact same problem.

## 6. Reflection

Think back on your bug reports:

- Which one was the clearest?
- What information did you initially miss?
- How did your classmate respond?
- What would you do differently next time?
